# Movie Memory

A small full-stack app for keeping a favorite movie and discovering a fun fact about it. Built for the Scowtt take-home exercise.

**Implemented: base + Variant A (Backend-Focused: Caching & Correctness).** Chosen to demonstrate user-scoped data ownership, precise cache expiry, concurrent-request handling, and graceful provider failures.

## What works in the code

- Google OAuth through Auth.js, backed by database sessions.
- First-time onboarding with server-side trimming and 1–200 character validation.
- Favorite movie stored in Postgres and linked to the authenticated user.
- Protected dashboard showing Google profile details, favorite movie, and a generated fact.
- Missing-name, missing/broken-photo, loading, and error states.
- OpenAI Responses API integration; successful facts must be saved before they are displayed.
- Logout revokes the database session.
- Responsive, keyboard-accessible interface.

## Local setup

Requires Node.js **22.12 or newer** and npm. The bundled local database helper works on supported macOS/Linux/Windows architectures and needs no Docker. Alternatively, use an existing Postgres database.

```sh
npm ci
npm run setup:local
npm run db:generate
```

`setup:local` creates a private, git-ignored `.env` with a random authentication secret and local database password. It never overwrites an existing `.env`.

In a separate terminal, start the local Postgres instance:

```sh
npm run db:local
```

The helper listens only on `127.0.0.1:55432`. Database files persist under `.local/postgres`, which is ignored by Git. Keep this terminal open. Ctrl+C stops Postgres without deleting data. The helper refuses to run against a remote database or a different local port/name.

Apply all checked-in migrations and start the app:

```sh
npm run db:migrate
npm run dev
```

Open **http://localhost:3000**. Use this hostname consistently for Google OAuth, rather than switching to `127.0.0.1` in the browser.

For an existing Postgres database, set `DATABASE_URL` and skip `db:local`. Use a dedicated empty database for this app before applying migrations. For a production build:

```sh
npm run build
npm start
```

The npm configuration uses `legacy-peer-deps` to avoid npm 10's observed peer-resolution crash involving optional tooling dependencies. Dependency versions are captured in `package-lock.json`; the install, TypeScript checks, and production build were validated together.

## Environment variables

Only `.env.example` belongs in Git. Never share the local `.env`, database directory, or Google client-secret file.

| Variable             | Purpose                                                                   |
| -------------------- | ------------------------------------------------------------------------- |
| `DATABASE_URL`       | Postgres connection string; generated for local development by the helper |
| `AUTH_URL`           | Canonical app origin; `http://localhost:3000` locally                     |
| `AUTH_SECRET`        | Random Auth.js secret; generated by the setup helper                      |
| `AUTH_GOOGLE_ID`     | Google OAuth **Web application** client ID                                |
| `AUTH_GOOGLE_SECRET` | Secret for that same Google OAuth client                                  |
| `OPENAI_API_KEY`     | Valid OpenAI API key with API access/billing                              |
| `OPENAI_MODEL`       | Defaults to `gpt-4.1-mini`; set a model your API project can access       |

### Google OAuth

1. In a Google Cloud project you own, configure the Google Auth Platform consent screen. Use only basic identity scopes: `openid`, `email`, and `profile`.
2. If the application is in testing mode, add the Google account you will use as a test user.
3. Create an OAuth client of type **Web application**.
4. Add this exact authorized redirect URI: `http://localhost:3000/api/auth/callback/google`.
5. If configuring authorized JavaScript origins, use `http://localhost:3000`.
6. Put the client ID and secret in `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` in `.env`.
7. Restart the app after changing environment variables.

Do not reuse unrelated or downloaded-example OAuth credentials without confirming ownership and the authorized callback. Google Cloud may require account setup and acceptance of its terms before these steps.

### OpenAI

Set a valid `OPENAI_API_KEY` locally and restart. The app sends the movie title and, on refresh, the previous generated fact to OpenAI—not the user's name or email. Requests require OpenAI web search, have a 30-second timeout, no automatic retries, and a bounded output length. Cache misses incur web-search tool charges as well as model usage. The configured model must support Responses API web search; the default gpt-4.1-mini was verified with the configured account. Provider-side response storage is disabled with `store: false`; successful facts are stored in our own database.

## Architecture overview

### Routes and request flow

This app uses Next.js App Router with React Server Components. The landing page (`/`) checks the session: logged-out visitors see the Google sign-in button; authenticated visitors are routed according to whether a favorite movie exists. `/onboarding` and `/dashboard` independently require authentication on the server. A user who signed in but abandoned onboarding is sent back to finish it, rather than treated as a fully onboarded returning user.

Auth.js handles Google's OAuth callback at `/api/auth/callback/google` and validates the OAuth flow. The application permits the Google provider only and requires Google's verified-email claim. The Prisma adapter maintains the user, linked OAuth account, and database session. Database sessions were chosen because logout can revoke them directly. The browser holds an opaque session token in an Auth.js-managed cookie, not a user ID supplied by the UI.

Google sign-in, onboarding, and logout use Server Actions. This keeps mutations beside the app, avoids an unnecessary custom API/client layer for the base exercise, and uses Next.js's action-origin protections. Every protected read and write still performs its own session check. Hiding a button is never treated as authorization.

The dashboard first renders the profile and movie; an asynchronous fact component sits behind a Suspense loading state. Every dashboard render and explicit refresh uses the same server-side 60-second cache policy. A fresh saved fact is reused; refresh does not bypass the window. Concurrent requests for the same user/movie share one promise in this server process. Provider failure returns the latest saved fact with a visible fallback notice, or a friendly retry message if none exists. A full page-level error boundary handles failures outside the fact component.

### Data model

`User` contains Google profile fields and nullable `favoriteMovie`. Null means onboarding is incomplete. A separate movie table is unnecessary for a single free-form favorite title: there is no movie catalog, normalization requirement, or third-party movie database. The title is trimmed, restricted to 1–200 characters, and stored as `VARCHAR(200)`. The server rejects control characters as well as blank/non-string/oversized input.

`Fact` contains `userId`, a snapshot of the movie title, text, generation timestamp, citation URLs/titles/text offsets, and a generation-policy version. Storing the title on each fact preserves the association when the user edits their movie. The `(userId, movie, createdAt)` index supports user-scoped retrieval and the Variant A cache. Cascading relations remove facts/accounts/sessions when their owning user is deleted.

The standard adapter models `Account`, `Session`, and `VerificationToken` are retained for Auth.js compatibility. The Google email is unique and mandatory; name and image remain nullable. The app does not enable automatic account linking by matching an untrusted email.

Onboarding updates only the session owner's row and only while `favoriteMovie` is null. A forged `userId` field is ignored. The conditional database update also prevents a repeated or concurrent onboarding submission from overwriting a movie that was already saved.

### Fact generation and failures

`generateAndSaveFact` is a small dependency-injected service. Production uses the OpenAI wrapper and Prisma; tests substitute the provider without making paid requests. The service rejects empty or excessively long responses and persists a successful fact before returning success. Database-save failures are not silently presented as successful saved facts.

The prompt separates fixed instructions from the movie-title data and requires web lookup, explicit film identification, and a short source-backed production fact. It considers worldwide cinema and asks for clarification if identification is uncertain. Output must include a completed search and safe URL citations; otherwise it is rejected. Citations are stored and rendered as inline clickable links. This is retrieval grounding, not an independent factual guarantee: source quality and model interpretation can still be wrong. Movie titles are rendered as text, never injected as HTML. Unknown, unsupported, or ambiguous movie titles return a friendly instruction to add a year, language, or actor rather than storing an uncited answer. Older generation-version-0 facts remain in history but are excluded from both fresh-cache and stale-fallback reads to prevent known unsourced answers from resurfacing.

The OpenAI and database modules are marked server-only. Provider error payloads and credentials are not sent to the browser or printed in application logs. On provider failure, the service returns the latest fact for this exact user/movie, preserving its original timestamp; without one it returns a friendly error. Failed cache reads produce a friendly error without calling OpenAI. Save failures preserve an older saved fact if available, and never claim that unsaved output was persisted. Authentication failures similarly expose a generic sign-in error.

### Interface and tradeoffs

The interface uses a neo-noir midnight palette with violet and pink accents, an illustrated ticket, and CSS artwork. Space Grotesk headings and Inter body text are self-hosted through next/font; the build downloads these fonts from Google. No external movie-poster service is required. React, Tailwind's CSS pipeline, and ordinary component styles provide responsive layouts, visible focus indicators, associated input errors, disabled pending buttons, reduced-motion support, and an avatar fallback.

The current scope implements Variant A plus a requested movie-editing convenience. The rest of Variant B, fact-history browsing, and deployment are excluded. The Edit movie form supports Save/Cancel, validates on the server, updates only the session owner, and revalidates the dashboard. Changing movies remounts the fact loading boundary and uses the cache for the new user/movie key; older facts remain scoped to their original title. Auth.js v5 is pinned to an explicit beta because it provides the App Router server-action API used here; the lockfile and tests make that choice visible and reproducible.

## Variant A: cache and concurrency decisions

- The authenticated entry point `getCurrentFact()` takes no identity or movie arguments. It resolves the session owner and current movie server-side. Both cache lookup and insert are scoped to that user/movie; request query parameters cannot select another user's facts.
- Query the newest matching fact by `createdAt DESC, id DESC`, supported by the existing compound index. Age is measured from the stored timestamp. Ages from 0 through 59,999ms reuse it; at exactly 60,000ms it expires. Reads and failures never reset that timestamp. Unexpected future timestamps are not considered fresh.
- A process-local promise map is keyed by the JSON-encoded `[userId, movie]` pair. The promise is registered before the cache read, so overlapping renders, refreshes, and tabs share lookup/generation/save. The entry is removed in `finally` after either success or failure; different users and movies can progress independently.
- **Limitation:** this is the assignment's explicitly permitted simple in-memory-lock approach. It protects one long-lived server process only. Multiple workers, replicas, or serverless instances can each generate for the same key; a restart also clears in-flight coordination. Facts themselves remain in Postgres. Before scaling out, replace this with a database transaction/advisory lock or a durable generation lease with expiry and ownership checks. It is not distributed exactly-once processing.
- OpenAI calls time out after 30 seconds and do not automatically retry. A later request can retry after a failed in-flight attempt; the lock is not a rate limiter. Cached/stale responses never create duplicate rows.
- Server time determines age; keep application and database clocks synchronized. The implementation retains historical facts without a retention policy, appropriate for this small exercise but a production cleanup policy would be needed.

With two more hours, prioritize a database-backed generation lease for multi-instance deployment, a second-account live OAuth check, and a recorded walkthrough of the cache and failure cases.

## Repeated-fact handling

After cache expiry, generation receives the last fact for this user/movie and asks for a different sourced claim, not a paraphrase. An explicit NO_DIFFERENT_FACT response or matching text after citation/case/punctuation normalization returns the previous fact with an unchanged status. No duplicate row is inserted and the original timestamp is preserved. The UI explains that no different fact was found. This comparison detects repeated text, not every semantic paraphrase; unique content is not guaranteed. No automatic extra paid retries are made.
